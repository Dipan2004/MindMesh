# CONFIG.md — Every Tunable Variable in One Place

Rule: if a number or model name is used more than once, it lives here and
in `src/graphrag_lite/config.py` — never hardcoded inline in a task's code.
When a task changes a default, update this table AND the changelog at the
bottom, so DOCUMENT.md entries can reference "CONFIG.md v(N)" instead of
re-explaining the value.

## 2. Extraction

| Variable | Default | Notes |
|---|---|---|
| `MAX_GLEANINGS` | 1 | **Evidence (2026-10-22, `tests/exp_pilot_15b.py`):** on `qwen2.5:1.5b` over the 2-doc / 13-chunk pilot, gleaning ON gives **60 entities / 33 relationships** vs gleaning OFF **48 / 28** — a gain of **+12 entities / +5 relationships** (25% / 18%). On `qwen2.5:0.5b` (canonical corpus) gleaning added **0** entities and **0** new unique (src,tgt) pairs: `data/cache/extractions.jsonl` and `data/cache/extractions_v2.jsonl` both total 96 entities / 53 relationships. **Recommendation:** `MAX_GLEANINGS=0` for the 0.5B model (measured zero benefit), keep the default `1` for 1.5B and larger (measured benefit). Each increment = 1 extra LLM call per chunk. **Variance caveat (2026-10-22, `tests/exp_determinism.py`):** `temperature=0.0` + `seed=42` did **not** reproduce byte-identical responses on 1 of 3 chunks (2 entities vs 14 from the same prompt), and the gleaning-OFF baseline for `transformer_architecture/2` was 2 entities in one run and 14 in another. The `+12 / +5` figure should therefore be read as **directional, not as an effect size**; the solid part of the claim is structural — `gleaning.py::_merge` is strictly additive, so gleaning can never *reduce* a count (0 chunks with OFF > ON across every run). |
| `EXTRACTION_MODEL` | same as `SLM_MODEL` (local mode) | Ablation: try extraction on Grok too, compare noise |
| `EXTRACTION_TEMPERATURE` | 0.0 | Greedy/deterministic. Keep at 0.0 for extraction and gleaning so cache hits are meaningful and results are stable across re-runs. Raise only if you want diversity in generation (not applicable for structured JSON extraction). |
| `EXTRACTION_SEED` | 42 | Fixed RNG seed. temperature=0.0 alone is not sufficient for determinism on all models/platforms — seed must also be set. Confirmed via stability test. |
| `LLM_NUM_PREDICT` | 4096 | Ollama `num_predict` — the hard cap on tokens generated per call. **Raised from 2048 on 2026-10-22.** The extraction failures were **truncations, not timeouts**: on `qwen2.5:1.5b`, chunk `a885be6b` came back with `done_reason=length`, `eval_count=2048` (exactly the cap) and unparseable JSON; at `num_predict=4096` the same chunk returned `done_reason=stop`, `eval_count=842`, in 101.8s and parsed cleanly. A chunk that finishes early costs no extra time, so a higher cap only costs wall time on chunks that were already broken. **Caveat:** a bigger cap does not fix a genuine runaway — chunk `4af3dc8c` hit the cap at *both* 2048 and 4096 and still failed to parse. Runaway chunks need a different fix, not a bigger cap. Keep `LLM_TIMEOUT_S` above the worst-case generation time for this cap. **Caveat:** a bigger cap does not fix a genuine runaway — chunk `4af3dc8c` is a degenerate repetition loop (one entity line repeated 83×) that still loops at 8192. Note also that `a4a679c4` was **not** a runaway at all: at 4096 it produced a *complete* 20-entity / 20-relationship extraction whose only defect was one trailing comma, and `_extract_json` now repairs that. The cap is reliably reachable as long as the request's *effective* context leaves room for the prompt plus the cap; `LLM_NUM_CTX=8192` guarantees this for the measured prompt sizes (403–558 tokens) — see `LLM_NUM_CTX`. |
| `LLM_THINK` | `auto` | Ollama reasoning/thinking mode: `auto` \| `on` \| `off`. `auto` does not send the parameter at all, leaving the model's own default. `off` sends `think=False`; `on` sends `think=True`. **qwen3-family models are reasoning models** — they return their chain-of-thought in a *separate* `thinking` field, which consumes the whole `num_predict` budget and leaves the visible `response` empty, so extraction returns nothing that parses (measured on `qwen3.5:2b`: 0/3 chunks parsed with thinking on, 1/3 with `think=False`; the 2 remaining failures were the same `num_predict` truncation, not a parse bug). Set `LLM_THINK=off` for any qwen3-family extraction model. The `think` parameter is a **top-level** Ollama parameter — a *sibling* of `options`, not a key inside it. `OllamaClient` also emits a warning if a response carries a non-empty `thinking` field that was silently discarded. |
| `LLM_NUM_CTX` | 8192 | Ollama runtime context window (`num_ctx`), sent per request in `options`. **Raised from the Ollama default of 4096 on 2026-10-22.** Controlled experiment (`tests/exp_numctx.py`, 2026-10-22): **4096 is NOT a hard wall on generation.** PROBE A generated **8750 tokens in one request** (`prompt_eval_count=558` + `eval_count=8192`) on a runner that `ollama ps` showed at CONTEXT=4096 — Ollama grows the runtime context to fit `num_predict`. But the bound *is* real for a request served by a runner still at 4096: `qwen3.5:2b` chunk 0 stopped at `eval_count=3693` = 4096 − its 403-token prompt, and PROBE B (the identical request with `num_ctx=8192`) reached the full `eval_count=4096`. So setting this is worth doing, but the mechanism is "the loaded runner's context is a floor for generation", **not** "4096 caps you at 4096". Diagnostic rule: `eval_count == num_predict` → `num_predict` truncation; `eval_count < num_predict` **and** `prompt_eval_count + eval_count` == the request's *effective* context → context exhaustion. Note `ollama ps` reports the **loaded runner's** context, which Ollama has been observed to grow across requests — it is not a per-request guarantee. Keep `LLM_NUM_PREDICT` below `LLM_NUM_CTX` minus the prompt size. |
| `LLM_FREQUENCY_PENALTY` | 0.25 | Ollama `frequency_penalty`, sent per request in `options`. **New on 2026-10-22.** The lever for **degenerate repetition loops** — the one failure mode a bigger `num_predict` cannot fix. Unlike `repeat_penalty`, which applies the *same* flat penalty to every token that has ever appeared, a frequency penalty scales with **how many times** a token has appeared, so the 84th copy of a line is penalised far harder than the first. That is the shape the pathology needs. Controlled experiment (`tests/exp_runaway_repeat_penalty.py`, `tests/exp_runaway_freq_penalty.py`, `tests/exp_freq_penalty_robustness.py`, `tests/exp_fp_penalty_choice.py`) on `qwen2.5:1.5b`, chunk `4af3dc8c`, `num_predict=4096`, 3 runs per setting: **no penalty → `eval=4096`, `done=length`, parse=FAIL 0/3** (a repetition loop: one entity line repeated 83×); **`repeat_penalty` 1.05 → 37×, 1.15 → 48×, still truncated and unparseable, and non-monotonic — a flat penalty does not work at all**; **`frequency_penalty` 0.25 → `eval=2583`, `done=stop`, parse=ok 3/3, 21 entities / 15 relationships, zero repetition**; 0.5 → parse=ok 3/3 but only 10 entities / 8 relationships; 0.75 → parse=ok 3/3 but only 8 entities / 3 relationships; 1.0 and 1.5 → the model abandons a record mid-field and the JSON is left unterminated (parse=FAIL). **Why 0.25 and not 0.5:** the chunk names ~22 real entities, and 0.25 recovers 21 of them, while 0.5 and 0.75 have merely traded the repetition for **under-extraction** — their apparent speed (25 s / 19 s vs 161 s) is the model *giving up early*, not the penalty being cheap. No regression on healthy chunks: `transformer_architecture/0` and `/2` returned the same entity and relationship counts with and without the penalty. Set to `0` to restore the pre-penalty behaviour exactly (the parameter is then not sent at all). **Scope of that claim (narrowed 2026-10-22):** "under-extraction" is a **within-chunk** comparison against one dense chunk in one run. Against the corpus as a whole, 10 and 8 entities are *above* the median — the 39 chunks that parsed in the corpus run have a **median of 5 entities** and 21 of 39 have fewer than 6. Do not read the 0.5/0.75 numbers as a corpus-level statement, and do not add a minimum-entity-count guard on the strength of them: it would reject more than half the legitimate extractions. **Caveat, measured on the full corpus (2026-10-22):** the penalty **reduces** the failure rate but does **not** eliminate it. `tests/exp_reextract_corpus.py` re-extracted all 42 chunks with `frequency_penalty=0.25` and parsed **39/42**; the 3 failures were all repetition loops. `4af3dc8c` — the chunk the penalty fixed 3/3 in isolation — **looped in the corpus run with the same settings**, because the model is **bistable**: it settles into one of several stable attractors depending on the server's numeric state, not on the prompt, seed, or settings. `tests/exp_reextract_failures.py` then showed the same chunk, same settings, **back-to-back in one process**, looping on one call and parsing on the next, with no cache in the path. It also **refuted the `num_ctx` hypothesis** (the corpus run's `ctx=8192` parses `4af3dc8c` 1/2, `ctx` unset 0/2) and showed the **failure rate is itself a sample** — the corpus run parsed 0/3 of those chunks, the probe re-running the identical settings parsed 2/6. **Control arm (added 2026-10-22):** the same corpus re-run with the parameter **not sent at all** (`fp=0`, `data/cache/exp_reextract_fp0.jsonl`) parses **35/42** — 7 failures, **6 repetition loops and 1 malformed JSON** (`done=stop`, 689 tokens, every line distinct, a *missing* comma, 35 s instead of 300 s; this quiet mode is easy to miss next to the loud loops). So the penalty is worth **+4 chunks net**, and the two arms **disagree on 8 of 42 chunks in both directions**: 6 parse only at `fp=0.25`, and 2 (`4af3dc8c`, `f08417a7`) parse only at `fp=0`. The earlier derived claim that "the penalty turned 3 failures into 0" was an inference from the `fp=0.25` arm alone and is **wrong**; it is corrected in `DOCUMENT.md`. The correct reading: the penalty **shifts the dice**, it does not make chunks safe, and **no single setting makes extraction reliable** — which is why the retry ladder, not the penalty, is the fix. Treat this knob as a mitigation and use the **retry with escalated settings** (`LLM_RETRY_FREQUENCY_PENALTIES`) on a failed chunk; do not treat a single successful extraction as evidence the chunk is safe. |
| `LLM_RETRY_FREQUENCY_PENALTIES` | `[0.5, 1.0]` | Ollama `frequency_penalty` escalation ladder, applied by `extractor.extract_entities_relationships` when a chunk's extraction **fails to parse**. **New on 2026-10-22.** The ladder is `[None] + LLM_RETRY_FREQUENCY_PENALTIES`: attempt 0 uses the client exactly as configured, and each later attempt re-issues the same prompt with the next listed `frequency_penalty`. **Why a retry and not a better single setting:** the model is **bistable** — it settles into one of several stable attractors depending on the server's numeric state, so the *same* chunk with the *same* settings parses in one session and loops in the next (measured: `4af3dc8c` passed 3/3 in isolation and then looped in the 42-chunk corpus run; and the isolated re-run of the same settings in `tests/exp_reextract_failures.py` looped again at `eval=4096`, `done=length`, 62 repeats). Changing the penalty is a **different decode**, and therefore a different attractor, so a retry has a real chance of landing in a good one. **Cost:** the worst case is 3× the wall time on a chunk that never parses (each attempt can burn the full `num_predict` budget); the common case is one attempt, since the ladder is only entered on a parse failure. Each attempt is a **distinct cache entry** (see `CACHE_DIR` / the cache key note in §9), so a retry is never served the first attempt's failed response. If the whole ladder is exhausted the last `ValueError` is re-raised and `scripts/build_index.py` records the chunk in `failed_chunks` — the failure stays visible, it is not swallowed. Set to `[]` to disable retries (a failed chunk is then recorded and skipped after one attempt). Covered by `tests/test_retry_ladder.py` (12 offline tests). **MEASURED END TO END (2026-10-22, later that day).** The corpus was re-run through the **production** path with this ladder (`tests/exp_reextract_corpus_ladder.py`, own `CACHE_DIR`, own outputs, detached, sequential because the model is bistable): **42 of 42 chunks parsed, 0 failures**, **245 raw entities and 171 raw relationships** — better than both no-retry control arms (`fp=0.25`: 39/42, 161 rels; `fp=0`: 35/42, 157 rels) on every axis. The **rescue rate** was measured separately, on the four chunks that are *known* to be hard, because a corpus run cannot answer that question (on any given run the failures are whichever ones the bistable model happened to lose): `tests/exp_ladder_hard.py` ran them through the production extractor 3 times, **each repetition with a fresh `CACHE_DIR` so it is a fresh decode and not a cache hit**: **P(attempt 0 fails) = 4/12 (33%), P(rescued given attempt 0 failed) = 4/4 (100%), P(chunk ultimately fails) = 0/12**. **Every rescue came from the first rung (`0.5`); the `1.0` rung was never needed.** **Two measured caveats.** (i) A **parse** success is not a **content** success: one of the four rescues (`4af3dc8c` at `fp=0.5`) came back with 8 entities and 8 relationship objects whose `source`, `target`, `type` and `description` were all **empty strings** — valid JSON, zero usable edges. The higher penalty buys parseability by pushing the model towards placeholders. (ii) The ladder does not touch a separate content defect: the extractor's endpoint-consistency filter drops **53 of the 171 relationships the model emits (31%)**, 45 of them because the model named an entity in a relationship that it did not also list as an entity (`DOCUMENT.md` open item 8). |
| `EXTRACTION_STUB_ENDPOINTS` | `false` | **New on 2026-10-22.** Conditional relaxation of the extractor's endpoint-consistency filter. When `true`, a relationship endpoint that is **not** in the chunk's entity list is **recovered** instead of dropped, *provided its name occurs verbatim in the chunk text* (casefold, whitespace-normalised, word-boundary bounded: `(?<!\w)…(?!\w)`, so `AI` does not match `AIDS` and `U.S.` does not match `U.S.A`). The recovered endpoint is added to the entity list with `type="OTHER"` and the marker attribute `stub=True`, and the relationship is kept; an endpoint whose name is **not** in the text is still dropped with the same warning as before. Wired through the extractor, the gleaning pass and the graph builder (node attribute `stub`; a node is a stub node only if *every* occurrence was a stub). **Measured on the ladder arm's raw responses, same responses parsed twice, no new LLM calls** (`tests/exp_stub_endpoints_measure.py`): 171 relationships emitted → **118 kept with the flag off, 163 with it on (45 recovered, 18 stub entities added)**; loss rate to the filter **31.0% → 4.7%**; **all 18** unknown endpoint names occurred verbatim in their chunk text and **none** was let through that the text does not contain. **Default OFF deliberately:** a dangling edge is the shape a hallucination takes, so the relaxation is opt-in and carries the recovered entity's weaker provenance into the graph. Covered by `tests/test_stub_endpoints.py` (17 offline tests). See `DOCUMENT.md` Item 10. |

## 5. Graph Retrieval (Pipeline B)

| Variable | Default | Range to test |
|---|---|---|
| `BFS_HOP_DEPTH` | 2 | 2–3 |
| `RANKING_METHOD` | `pagerank` | alt: `degree` — must A/B both, PRD §9 |
| `PAGERANK_DAMPING` | 0.85 | standard NetworkX default; read from config for ablation |
| `TOP_N_CANDIDATES_AFTER_RANKING` | 20 | before second Zvec pass |
| `TOP_N_FINAL_EVIDENCE` | 6 | passed to the LLM |
| `PIPELINE_B_SIM_WEIGHT` | 0.85 | Weight of the **query-dependent** similarity term in the candidate score. The Zvec RRF score is normalised against the best entry-point score *before* weighting — raw RRF scores are ~0.016–0.033 while normalised PageRank is ~0–1, so an unnormalised mix lets PageRank dominate ~30:1 and one high-PageRank node wins most queries. Measured effect of the fix (2026-10-22, 10 gold queries): distinct top-1 candidate **3 → 6**. Set to 1.0 to make PageRank a pure tiebreak. |
| `PIPELINE_B_PR_WEIGHT` | 0.15 | Weight of the **query-independent** PageRank term. Small, so it only breaks ties between equally query-relevant candidates. Must sum to 1.0 with `PIPELINE_B_SIM_WEIGHT`. |
| `PIPELINE_B_DROP_TYPE_LABELS` | `true` | Removes generic taxonomy nodes (`Person`, `Organization`, `Edge`, ...) from the *ranked candidates*, not just from the entry points — BFS can reintroduce them. These are the highest-PageRank nodes in the graph and are never meaningful retrieval targets. Measured effect: type-label nodes surviving into the ranking went from 2 queries to **0**. |
| `PIPELINE_B_SCOPE` | `docs` | How far the second (scoped) Zvec query reaches. `docs` = the re-query is restricted to the candidates' source **documents**; `candidates` = restricted to the **chunks in which the ranked candidates were mentioned**; `verbalized` = PRD §9 Step 3 verbatim — the candidates are verbalized (`name (TYPE): description`) and that text becomes the **dense** side of the second query, while the lexical/BM25 side stays the user's query. Measured on the 10-query gold set (2026-10-22): `docs` recall@6 **1.00**, gold at rank 1 **10/10**; `candidates` **0.73**, 8/10; `verbalized` **0.73**, 4/10 (mean best gold rank 1.88). The default is the measured behaviour, not the PRD's wording — see DOCUMENT.md Item 14. |

## 9. Caching

| Variable | Default | Notes |
|---|---|---|
| `CACHE_BACKEND` | `diskcache` (SQLite-backed) | key = `sha256(model + "\x00" + cache_tag + "\x00" + prompt)`. **`cache_tag` added 2026-10-22** — it is empty by default, which reproduces the historical key exactly (so the entries that survived the cache wipe stay reachable), and it carries the generation settings (`temperature`, `seed`, `num_predict`, `num_ctx`, `frequency_penalty`, `think`) when the caller supplies one. The old key was `sha256(model + "\x00" + prompt)` and could not tell two calls with the *same* prompt and model but *different* settings apart, so a response generated under one setting was silently served under another. That mattered for the retry ladder: without a tag, a retry with an escalated penalty was handed the first attempt's failed response and changed nothing. |
